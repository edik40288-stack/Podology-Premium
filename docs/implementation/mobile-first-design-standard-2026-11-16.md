# Мобильная и десктопная дизайн-система: подология (2026-11-16)

Статус: **внедряемый стандарт и QA-критерии**, не сертификат соответствия WCAG.

## Пользовательские роли и главные действия

| Поверхность | Телефон: главная задача | Первое действие |
|---|---|---|
| Публичный сайт | Найти услугу, понять цену, записаться | «Записаться на приём», заметная кнопка |
| Кабинет клиента | Услуги, запись, предстоящие визиты | «Записаться», «Мои записи», «Моя карта» |
| Специалист CRM | Сегодняшние записи, визит, карта, фото, рекомендации | Ближайшая запись / карта |
| Администратор CRM | Расписание, создание/перенос записи, оплатa | Расписание / новая запись |
| Управляющий CRM | Загрузка смен, материалы, команда, задачи | Операционные исключения |
| Владелец CRM | Финансы, план-факт, отчеты, подтверждение операций | Расшифровка показателей |

Не подменять рабочую CRM компонентом DemoWorkspace. Не изменять бизнес-правила, D1, расписания или права при визуальных правках.

## Визуальные и технические правила

1. 320–430 CSS px: **одна основная колонка**; по 14–18 px горизонтальные поля. От 600/768 px переходные двухколоночные композиции только там, где содержимое остается читаемым. На 1024+ использовать полноценную навигацию по доступной ширине, не по названию устройства.
2. Основной текст мобильной CRM и кабинета: 15–16 px с line-height 1.5–1.65. Второстепенные пояснения 12–13 px, но **не** 7–9 px. Заголовки секций 18–22 px, страницы 26–32 px. Денежные суммы имеют табличные цифры и отдельный вес/контраст.
3. Иерархия: H1 = одна главная идея экрана; H2 = самостоятельный рабочий раздел; поля/описания обычным начертанием; primary CTA максимум один визуально доминирующий на смысловой блок. Статус и предупреждение обозначать не одним цветом, а иконкой/текстом.
4. Тач-цели: проектная цель минимум 44x44 CSS px и зазоры 8–12 px. Это эргономический запас сверх порога WCAG AA 24 CSS px (с оговоренными исключениями). На iOS Apple рекомендует 44x44 pt; это не норматив CSS-пикселей.
5. Контраст текста: минимум 4.5:1 для обычного, 3:1 для крупного текста по WCAG AA. Не назначать бледно-зеленые подписи на бледно-зеленом фоне без проверки. UI-фокус и ошибки показывать явно.
6. Длинные табличные данные: не обрезать столбцы и кнопки; применять таблицу со своим прокручиваемым контейнером и видимой подсказкой. Рабочие табы лучше переносить в строки/сетку с целыми подписями.
7. В клиентском кабинете на узком экране доступны главные четыре действия; дополнительные экраны открываются через «Все разделы». Нижняя навигация учитывает safe-area и не должна скрывать содержимое.
8. Скриншоты на 320, 375, 390, 430, 768, 1024, 1280/1440; нужны действительные потоки владельца, управляющего, администратора, специалиста и клиента, а не только публичная заглушка.
9. При 200% увеличении текста проверять, что кнопки, надписи, поля и предупреждения не перекрываются. Таблицы являются допустимым исключением из правила reflow, остальные блоки не должны создавать прокрутку всей страницы по X.
10. Системный font stack: Manrope для брендовой подачи при доступной загрузке, затем `system-ui,-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,Arial,sans-serif`; не фиксировать одинаковые 7–9 px на iOS, Android, Windows.
11. Сохранить жесткие запреты: не смешивать открытое портфолио DIKIDI с защищенными клиническими фотографиями, не подделывать свободные слоты и реальные остатки.

## Критерии приемки

- Нет ошибки/пустого состояния приложения и нет горизонтального скролла документа на 320–1440 px (внутренний скролл таблицы допустим).
- Основная навигация доступна с телефона, открывается/закрывается через тап и Escape, клавиатурный фокус не уходит в закрытую панель.
- Операции на основных экранах и названия разделов полностью видны. В финансовых и складских табах нет усечения текста.
- Первичная кнопка записи/создания не перекрывает поля и контент. Поля доступны при экранной клавиатуре и увеличении текста.
- Текст/кнопки/иконки проверены по визуальным снимкам и геометрии DOM, не только ширине `document.documentElement.scrollWidth`.
- Каждая роль протестирована с фактически разрешенными действиями и запретами ACL отдельно от CSS.
